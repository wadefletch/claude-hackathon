# Agent Design — Chicago Low-Income Housing Search

Owner: Jonathan. Scope: the conversational agent that turns a user's freeform
input and slider filters into a ranked, mapped set of housing options, and
gives them a self-reported read on affordable-housing eligibility along the
way. This covers only the agent slice of the platform — web (Rob), map
(Wade), data (Justin), foundation (Delores), and demo/profile (Lydia) are
separate workstreams this design integrates with but does not specify.

## Architecture

The agent is a single Vercel AI SDK tool-calling loop (`streamText` + tools),
not a custom state machine. One system prompt describes the task; the model
decides, turn by turn, whether to ask a clarifying question in plain text,
call a tool to fetch data, or call `show_map` to produce output. There is no
separate "clarify" or "search" phase coded by hand — that behavior emerges
from the system prompt and tool availability, same as any standard AI SDK
agent.

The agent does not perform geospatial computation itself. Commute
calculation and geocoding are owned by Wade's map/routing work; listings and
amenity data are owned by Justin's data pipeline. The agent's own
contribution is: (1) turning freeform text + slider state into a structured
query, (2) calling the right tools with that query, (3) using judgment to
rank/trade off the results (cost vs. speed vs. amenity fit — this weighing is
the model's job, not a fixed scoring formula), and (4) emitting `show_map`
with the ranked result.

## Tools

Only `show_map` is implemented by the agent. The rest wrap capability owned
by teammates; until that capability exists, they are stubbed with
hand-built fixture data matching the schemas below, so the AI SDK wiring is
demoable end-to-end today and the stub swaps out for the real implementation
later without changing the agent's prompt or tool-calling logic.

| Tool | Owner | Input → Output |
|---|---|---|
| `geocodeWorkAddress` | Wade | freeform address → `{ lat, lng }` |
| `computeCommute` | Wade | `{ origin, destination, mode }` → `{ distanceMiles, durationMinutes }` |
| `searchListings` | Justin | filter criteria → `Listing[]` |
| `nearbyAmenities` | Justin | `{ lat, lng, radiusMiles, types }` → amenity list |
| `assessEligibility` | Agent | `{ annualHouseholdIncome, householdSize }` → `{ amiTier, eligiblePrograms }` |
| `show_map` | Agent | `{ filters, rankedListings }` → writes to shared app state |

`assessEligibility` is a static lookup against published Chicago-area Area
Median Income (AMI) limits (extremely-low / very-low / low income tiers) —
no external call, no geospatial data. Rent-to-income ratio is not a tool at
all: it's plain arithmetic (`listing.price * 12 / annualHouseholdIncome`)
done inline while assembling `rankedListings`, then handed to the model as a
fact it can weigh in `rationale` alongside commute and amenities — same
treatment as any other tool-supplied fact under the "agent judges, tools
compute" split.

## Data contracts

**Filter/query object** — extracted by the agent from freeform text + slider
state before calling tools:

```
{
  workAddress: string,
  maxCommuteMinutes: number,
  travelMode: "walk" | "bike" | "bus" | "train" | "car",
  optimizeFor: "cost" | "time",
  householdSize: number,
  numKids: number,
  kidsAges: number[],
  budgetMax?: number,
  notes?: string
}
```

**Eligibility profile** — separate from the filter object because it's
sensitive, self-reported, optional, and used for informational scoring
rather than filtering listings in/out. Not persisted beyond the chat
session:

```
{
  annualHouseholdIncome?: number,
  receivesBenefits?: ("SNAP" | "Medicaid" | "Medicare")[],
  citizenshipStatus?: "citizen" | "non-citizen" | "prefer-not-to-say"
}
```

**Listing** — returned by `searchListings`, echoed inside `show_map`:

```
{
  id: string,
  address: string,
  lat: number,
  lng: number,
  price: number,
  bedrooms: number,
  bathrooms: number,
  neighborhood: string,
  sqft?: number
}
```

**`show_map` payload**:

```
{
  filters: <filter/query object>,
  rankedListings: [
    {
      listing: <Listing>,
      commute: { distanceMiles: number, durationMinutes: number, mode: string },
      nearbyAmenities: Amenity[],
      rentToIncomeRatio?: number,   // omitted if no income was provided
      rationale: string   // agent's own explanation for this ranking position
    }
  ]
}
```

`rationale` is where the agent's ranking judgment is visible — it is
generated by the model, not computed by a scoring function.

## Onboarding and eligibility

The chat can start from a suggested prompt (e.g. "See if you qualify")
instead of a blank input — a UI affordance Rob's chat implements, not a
separate flow the agent codes. Sending that canned message is just the
first user turn; the same single tool-calling loop handles it, with the
system prompt telling the model to lead with eligibility-relevant questions
(income, household size, benefits enrollment, citizenship) when a
conversation opens that way, and with housing-preference questions
(commute, budget, schools/grocery access for kids' ages) otherwise. Both
threads can surface within one conversation — nothing here forks the
architecture.

When the model has enough for an eligibility read, it calls
`assessEligibility` and reports the likely AMI tier and matching program
types, folds `rentToIncomeRatio` into its listing rationale where income was
given, and always states plainly that this is a self-reported estimate, not
an official determination — the real qualification decision happens at the
Chicago Housing Authority, and the agent includes a link to apply there.
Map results are never gated on the eligibility outcome: a user who declines
to answer, or who doesn't clearly qualify, still sees ranked housing
options.

## Handoff to the map

`show_map`'s result is written into shared app state (owned by Rob's web
layer — exact store/context mechanism TBD with Rob). Wade's MapLibre
component subscribes to that state and renders from it. The map never calls
the AI SDK directly, and the agent never touches map rendering — the
`show_map` payload shape above is the entire contract between them.

## Cross-team dependencies

- **Justin (heavy)** — geocoded static files for listings and Chicago
  amenity layers (parks, schools, grocery stores) from the Chicago Data
  Portal, matching the `Listing` and amenity shapes above. This is the long
  pole for the agent to go from stubbed to real; agent tools are built
  against these shapes now and swapped once files land.
- **Wade (heavy)** — `geocodeWorkAddress` and `computeCommute` covering all
  five travel modes, plus agreement on the exact shape his map component
  reads from shared state so `show_map`'s output matches what he consumes.
- **Rob (light)** — where the agent's API route lives in the TanStack Start
  app, and what the shared state mechanism is so `show_map` can write
  somewhere Wade's map can subscribe to.
- **Delores (light)** — Anthropic API key wired into env vars for the AI SDK
  calls.
- **Lydia (light)** — the exact household/customer-profile fields she's
  capturing (household size, kids + ages, other needs) so the filter schema
  above matches what her UI captures, plus a few example freeform queries to
  sanity-check clarifying-question behavior against. Also the current
  Chicago-area AMI limit figures per household size (for `assessEligibility`)
  and the actual URL to link to for applying through the Chicago Housing
  Authority — both are content/product decisions, not something to
  hardcode without checking.

## Out of scope

- Map rendering, routing/commute computation internals, and geocoding
  internals (Wade's).
- Listings/amenity data sourcing and storage (Justin's).
- Chat UI, API route placement, shared state implementation, and the
  suggested-prompt onboarding affordance (Rob's).
- Customer profile UI, demo scenarios, and sourcing the actual AMI figures
  and CHA application link (Lydia's).
- Deployment/env/secrets plumbing beyond needing the Anthropic key
  (Delores's).
- Actually determining housing eligibility. The agent only estimates a
  likely AMI tier from self-reported numbers and points the user to the
  Chicago Housing Authority for a real determination; it never blocks or
  filters map results based on that estimate.
- Persisting eligibility profile data beyond the chat session — no storage
  of income, benefits, or citizenship status is designed here.
